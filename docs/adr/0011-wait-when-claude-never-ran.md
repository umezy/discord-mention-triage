# ADR-0011: モデルが動く前のエラーは、失敗として数えずに待つ

## 背景と課題

- 2026-10-04 15:49 から、`claude -p` が 1〜6 秒で終わる失敗（終了コード 1、費用 0）を繰り返した。10-05 に再現すると、API が
  `403 oauth_not_allowed_for_organization` で拒否していた（Claude Code の文言は "Your organization has disabled Claude subscription
  access for Claude Code …"）。モデルは一度も動いていない。
- この文言は、認証切れ・利用枠切れを見分ける正規表現に当たらなかった。「仕分けの失敗」として 3 回ずつ数えられ、5 件が `failed/` に退避された。
  原因が直っても、退避した分は自動では処理されない。
- 実行記録には `claude_exit_1` としか残らず、原因は、手で再現するまで分からなかった。
- 指示文に入るのは、ファイルのパスだけ。メンションの本文は、モデルが動き出してから道具で読む。なので、
  **費用 0 のエラーは、届いた件の中身のせいではない。**

## 決定

- Claude Code がエラーを返し、費用を 0 と報告した回（`is_error` かつ `total_cost_usd == 0`）は、**文言によらず「待機」にする。**
  claim を `inbox/` に戻し、試行回数を数えず、新しい仕分けをしばらく止める。
- 文言の正規表現は、通知文と待ち時間の出し分けにだけ使う（認証切れ 10 分、利用枠切れ 30 分、どちらでもない `claude_not_started` 10 分）。
  モデルが動いたあとの認証切れ・利用枠切れは、これまでどおり文言で見分ける。
- この場合に限り、Claude Code のエラー文の先頭 200 字と、API のエラーの種類を、実行記録（`cli_error` / `api_error`）と通知に載せる。
  モデルが動いた回の結果は、本文が混ざりうるので、これまでどおり載せない。
- 待機の回数に、上限は置かない。

### 結果

- 得るもの: 契約や組織の設定、API の障害、モデル名の誤りなどで止まっても、届いた分は `inbox/` に残り、直れば自動で処理される。
  何が起きたかが、通知と実行記録で分かる。
- 引き受けるもの: 原因が直るまで、10 分おきに起動を試み（費用 0）、1 時間に 1 回通知する。上限は無い。その件を諦めるときは、手で `failed/` へ移す。
- 前提: 指示文に本文を載せない。これを変えるときは、この決定を見直す（`tests/test_run_claude.py` が、指示文に本文が無いことを検査する）。
- 残るもの: Claude Code が JSON を返さずに落ちる失敗（引数の誤り、起動時のクラッシュ）は、いまも失敗として数え、原因の文言も残らない。

## 採らなかった案

- 正規表現に、今回の文言を足す: 次の未知の文言で、同じことが起きる。
- 待機の回数に上限を置く（N 回で `failed/` へ）: 長い停止（今回は 1 日以上）で、結局取りこぼす。上限は、入力が原因の失敗を止めるためのものだが、
  上の理由で、費用 0 の失敗に入力は関係しない。
- ほかの件が成功したのに、同じ件でまた費用 0 になったら、その件だけ数える: 1 回の実行に複数の件をまとめるので、どの件のせいかを分けられない。
  部品が増えるわりに、効く場面が無い。
- 費用が分からない回（JSON を返さずに落ちた回）も待機にする: モデルが動いたあとに落ちた可能性があり、入力が原因でありうる。これまでどおり数える。
